# Bot 設計 QA：運作方式與尚未解決的問題

2026-10-14｜本輪只補 QA，不宣稱已完成可落地的 system design。

行為樹與資源鎖仍是第一版的必要架構。LLM、JEV／KEV、agent memory 全部 pending，本輪不定義其接口、實作或模型選型。

## Q1. 上一版到底哪裡沒有想清楚？

最大的缺口是：**我定義了「舊動作完全停止，才把資源交給新動作」，卻沒有證明現有插件提供足夠的停止能力。**

核對本機程式後：

- `mineflayer-pvp` 的 `stop()` 會停止追擊並等待事件，但攻擊還有自己的延遲佇列、視角 Promise 與盾牌計時器。公開的停止完成，不等於已明確回收所有內部工作。
- `forceStop()` 清除目標與尋路，也沒有提供「所有舊工作都已結束」的完成通知。
- Mineflayer 的 `deactivateItem()` 會送出停止使用物品的操作，但本機實作沒有直接結束 `consume()` 正在等待的 Promise。

這不證明每次取消都會出錯；它證明我不能只寫 `await stop()` 就宣稱競態已經解決。

也不能反過來說「所有 Promise 都必須結束才釋放鎖」：有些 Promise 剩下的只是等待結果，不會再操作 bot。真正要確認的是 **舊工作還能不能改變移動、視角、手持物或新任務狀態**。上一版把這兩者混在一起了。

## Q2. Gemini 的 review，我認同哪些？

認同行為樹、Blackboard、資源仲裁、固定優先級，以及保留 JS／CommonJS。非同步交接與部分資源搶佔也是必須處理的問題。

但有四項需要修正：

| 說法 | 較準確的理解 |
| --- | --- |
| 生存反應保證在 50ms 內 | 分層可以避免等待 LLM，但反應仍受感測、決策排程、尋路運算、插件停止與伺服器延遲影響；尚無實測，不能保證 |
| BT 不能跑 20Hz，否則尋路抖動 | 問題是反覆重設相同尋路目標；20Hz 檢查但不重設可以，5Hz 每次重設也可能有問題 |
| 60 行 selector 就等於完整系統 | 簡單 selector 可以很短；Sequence、Parallel、取消、資源交接及插件適配仍需另外實作與測試 |
| Blackboard 讓模組零依賴 | 它集中資料交換，但模組仍依賴約定的資料格式與更新責任 |

這份 review 引述的 `arbitrator.acquire()`、TypeScript 和 Utility AI 範例來自舊的 [reviews-by-ai.md](reviews-by-ai.md)，不是目前 proposal 的程式範例；其中指出的工程風險依然適用。

## Q3. BT 只是定義架構嗎？實際遊戲規則放哪裡？

分成三部分：

| 部分 | 放什麼 | 例子 |
| --- | --- | --- |
| BT 核心 | 樹的通用執行規則 | 優先選擇、依序執行、同時處理、檢查條件 |
| 遊戲子樹 | 何時做什麼、先後順序 | 低血且有威脅就撤退；安全時跟隨或撿拾 |
| 動作 | 實際操作 Mineflayer | 設尋路目標、換武器、吃東西、攻擊 |

例如「Sequence」只知道上一個步驟成功後才執行下一步；「戰鬥子樹」決定步驟是確認武器、接近敵人、攻擊。BT 核心不需要知道什麼是殭屍。

預計把上一版集中在一個檔案的遊戲規則，明確拆成以下組合：

```text
Parallel：兩個分支都持續檢查
├─ 主要行為：按下面的優先順序選一個
│  ├─ 生存子樹：有急迫危險 → 選撤退位置 → 拉開距離
│  ├─ 戰鬥子樹：需要自衛 → 準備武器 → 接近與攻擊
│  └─ 工作子樹：快落隊先跟上，安全時撿拾，否則跟隨或待機
└─ 維護子樹：需要時進食，安全時整理裝備，否則待機
```

「同時檢查」不代表全部都能操作 bot；真正執行仍要拿到相應資源。因此生存子樹可以負責撤退，維護子樹負責吃飯。

## Q4. 如何新增生存、戰鬥或工作子樹？

遊戲規則分別放在 `bt/subtrees/survival.js`、`combat.js`、`work.js`、`maintenance.js`，由 `bt/companion-tree.js` 明確組合。這些是預計的檔案，尚未建立。

每個子樹提供四件事：何時適用、如何選目標、由哪些節點組成、什麼情況結束或中斷。動作另宣告需要的資源與停止方法。

例如以後加伐木：在工作子樹加入「任務是伐木 → 找樹 → 接近 → 裝工具 → 挖掘」；已有導航與裝備動作可重用，挖掘動作需要新增。還要補上「伐木中遇敵」的中斷驗證，不能只新增一個檔案就宣稱完成。

生存與戰鬥仍排在工作前面，所以不必在伐木內重寫一份反擊邏輯。只有需要新的樹節點語義或新的控制資源時，才修改 BT 核心或仲裁器。

## Q5. Follow 實際怎麼運作？

1. 主人下達 follow，命令入口記住「持續跟隨這個玩家」。這是長期任務。
2. 感知資料記錄主人是否可見、目前距離及周圍威脅。
3. 沒有急迫危險或自衛需求時，主要行為選擇工作子樹中的 Follow。
4. Follow 取得 MOVE 和 LOOK，設定一次動態跟隨目標。後續檢查是在看要不要繼續，不是每次重新開始尋路。
5. 太遠才開始走、靠近後才停，使用兩個不同距離門檻，避免站在同一條邊界上走走停停。主人消失就停止追蹤，等待重新看見。
6. 如果此時餓了，維護子樹可另外取得 HAND 和 INVENTORY 吃飯；前提是導航不會挖方塊、放方塊或切換手持物。

**預防問題的 coding 技巧**：保留同一次動作紀錄、只在目標或行為真的改變時更新尋路，以及開始／停止使用不同距離門檻。

## Q6. 自動防禦反擊怎麼接手？

1. 感知發現近距離威脅，或收到受傷事件後重新檢查周圍。
2. 若已屬需要逃跑的危險，優先選生存子樹；否則選戰鬥子樹。
3. BT 撤回 Follow 的執行要求，但保留主人的跟隨任務。
4. 戰鬥要求 MOVE、LOOK、HAND、INVENTORY。仲裁器停止衝突的跟隨／進食／換裝動作，確認已不會繼續操作後，才一次授予整組資源。
5. 戰鬥在同一個擁有者下完成換武器、接近與攻擊，限制追擊距離。敵人消失、已離開威脅範圍或追擊超限，就結束戰鬥。
6. 下一輪依最新世界資料恢復跟隨，不從之前暫停的程式行數繼續跑。

**需要說清楚的限制**：`entityHurt(entity)` 告訴我們誰受傷，單靠它不能確定攻擊者。第一版可先針對附近符合威脅條件的敵對生物自衛，不憑「最近的人」猜攻擊者；玩家反擊與可靠的傷害來源識別另列未定事項。

**coding 技巧**：長期任務與當前動作分開保存；戰鬥用同一動作擁有者管理完整資源集合；操作前重新檢查敵人是否仍有效。現有 PVP 插件是否能符合停止契約，尚未完成驗證。

## Q7. 打到一半要逃跑，如何避免腳逃了、手還在打？

1. 生存條件成立，ReactiveSelector 在下一次檢查時選擇生存子樹。
2. Retreat 需要 MOVE、LOOK；它的優先級高於 Combat。
3. 仲裁器中止**整個 Combat 動作**，不是只拿走它的 MOVE。Combat 原本持有的四項資源一起進入停止處理。
4. 確認戰鬥不再發出操作後，Retreat 取得 MOVE、LOOK；如果此時適合進食，Eat 取得 HAND、INVENTORY。
5. 拉開距離後，仍需一段安全確認才解除撤退狀態，避免剛跑遠一點就回頭再打。若威脅持續，不因主人還在 follow 模式就硬衝回去。

**coding 技巧**：整組取得與整個動作取消、固定優先級、不同的進入／退出門檻。停止中的資源仍保留給舊動作清理，新動作不能提前操作。

「逃跑」也不只是把目標設在敵人反方向：還要排除明顯危險與不可達位置。第一版可先評估附近少量候選站立點，按遠離威脅程度與可達性挑選；退路品質、陷入角落與多敵人情境仍需要遊戲驗證。這裡不能宣稱一定逃得掉。

## Q8. 資源鎖到底用什麼資料結構？

以 Map 記錄「移動現在屬於誰、手現在屬於誰」；每個動作用 Set 列出它需要的完整資源。另一個 Map 記錄動作的執行與停止狀態。

每輪把請求按固定優先級排序，同級保留原擁有者；選出資源互不衝突的組合。取得全部所需資源才開始，不能拿著一半等另一半。需要交接就先停止衝突動作，完成後重看最新要求，再授予資源。

跟隨需要 MOVE＋LOOK，吃飯需要 HAND＋INVENTORY，所以可以一起執行。兩個都要 MOVE 的導航動作不能一起執行。這是程序內的控制權管理，不是作業系統的執行緒鎖。

## Q9. 那段難懂的主迴圈描述，白話是什麼？

> 平常大約每十分之一秒檢查一次：現在發生什麼事、哪些行為該做、誰可以操作 bot。走路和吃飯開始後，讓它們繼續進行；下一次檢查不必等它們完成，也不會重新開始同一個動作。受傷時可以要求提早檢查。舊任務晚到的結果不能改掉新任務。

對應的詞分別是：

| 原詞 | 白話與理由 |
| --- | --- |
| physicsTick 分頻 | 利用 Mineflayer 的物理更新通知，約每兩次做一輪決策；不是自己重寫物理運算 |
| 拍快照 | 這一輪所有節點讀同一份整理好的資料，避免前後判斷用不同版本 |
| tick BT | 從樹的入口依規則檢查目前應該執行哪些分支 |
| reconcile 資源 | 比較現在的擁有者與新要求，決定繼續、停止、等待或啟動 |
| 禁止決策重入 | 一輪尚未完成時，新事件只記下「還要再檢查」，不插進一半的決策 |
| 長操作存於 run | 每次動作有紀錄，知道它正在做、停止中、成功或失敗 |
| 不 await 在主迴圈 | 不把「等吃完」寫在這輪決策中；吃飯可以自己等待，決策仍繼續處理危險 |
| token | 每次授權的編號；舊動作帶舊編號，不能改新動作的狀態或釋放新鎖 |
| session generation | 每次重生／重新連線換一個編號，辨識上一條命的過期結果 |

這些編號只能防護**經過我們檢查的程式碼**。插件內部自行操作 bot 的回呼不會因此自動受控，這正是 Q1 的缺口。

## Q10. 主迴圈不等待，就真的不會卡嗎？

不是。等待網路的非同步操作通常不占著 JavaScript 執行，但同步尋路計算、過大的掃描或過量日誌仍會拖慢整個程序。

因此會限制觀察範圍與尋路運算預算，記錄「收到危險 → 決策 → 發出停止 → 取得控制權」各段耗時。10Hz 是初始排程選擇，不能拿它當作已證明的遊戲反應時間。

## Q11. 還沒解決的插件交接，下一步如何驗證？

先驗證三個小場景，還不需要整隻 bot：

1. 尋路中要求停止，隨即改成另一個導航動作；檢查舊的完成通知是否影響新目標。
2. 攻擊／換武器中要求撤退；檢查停止後是否還有舊的瞄準、攻擊或切換物品操作，並測同一敵人再次開戰的情況。
3. 進食中被中斷，再開始換武器或另一輪進食；分清「物品使用已停止」與「舊 Promise 還沒完成」，檢查舊結果是否污染新動作。

每個場景都要記錄實際 API 操作與所屬動作，不能只看鎖表正確。對隱藏回呼無法可靠取消的插件，選擇建立可追蹤的適配／維護修正版，或改用自己管理的基本操作；選定前不宣稱現成 PVP 已能直接接入。不以等固定幾百毫秒當作停止證明。

測試會先用可控制完成順序的 fake action 驗證仲裁，再到 Paper 驗證實際插件。等待純通知的 Promise 可以保留到它自然結束，但只有在確認它不會再控制 bot、結果也已隔離時，才能提早交接。

## Q12. 現在到底定了什麼，還有什麼 pending？

| 狀態 | 內容 |
| --- | --- |
| 已確定方向 | JS／CommonJS、真正的反應式 BT、生存／戰鬥／工作子樹、Blackboard、可搶佔資源鎖、五項首批功能 |
| 可說明但未實作 | 分支組合、整組資源仲裁、任務與動作分離、動作編號與舊結果隔離 |
| 尚未證實 | 現有插件的停止契約、並行時的實際副作用、撤退路線品質、反應時間與遊玩效果 |
| Pending | LLM、JEV／KEV、agent memory 的角色細節、接口、模型與儲存技術；不預建其模組 |

因此，本輪提供這份 QA；原 proposal 仍是待修訂草案，不能當作插件交接已解決的完整 system design。
