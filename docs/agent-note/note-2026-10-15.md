## 一、 Stage 3 開發目標與規格概述 (Stage 3 Overview)

Stage 3 核心目標為實現生產級的高強健度導航跟隨能力（Follow Functionality），滿足以下操作規範與行為特徵：
* **指令控制與權限隔離**：支援主人透過聊天室發送 `follow`、`unfollow` 與 `stop`，平滑切換 `FOLLOW` 與 `STAY` 意圖，拒絕非主人操作。
* **跟隨距離與高度遲滯門檻**：
  * `NormalFollow`：進入門檻 `distance > 2.2`，退出門檻 `distance <= 1.2` 且高度差 `|dy| <= 1.2`，確保緊跟在 1 格內且包含高度對齊。
  * `CatchUpFollow`：遠距離急追門檻 `distance > 16`（Priority 40），接近至 `<= 5` 格交棒給一般跟隨。
* **地形跨越能力**：自動辨識並越過 1 格高方塊、半磚（Slabs）、樓梯（Stairs），並支援梯子（Ladders）與藤蔓（Vines）攀爬。
* **門的主動通過與防抖動機制**：在封閉門前主動開啟木門/柵欄門/活板門，不依賴易出錯的第三方插件，開門後平滑走過，門開後絕不重複觸發關門。
* **可觀測性日誌**：記錄詳細運作軌跡至 `logs/bot-{id}-{date}.log`。

## 二、 開發迭代歷程與問題排除 (Development Iterations & Debugging)

### 迭代 1：指令解析與日誌系統建立
* **問題**：使用者發送 `follow` 無回應，且無實體日誌檔案可追查機器人內部決策。
* **處理**：
  * 重構 `src/commands.ts`，支援公開聊天與密語，加入前綴空白過濾與大小寫不敏感驗證。
  * 實作 `src/logger.ts`，格式為 `[YYYY-MM-DDTHH:mm:ss.sssZ] [LEVEL] message`，自動依日期輪轉輸出至 `logs/bot-{botName}-{YYYY-MM-DD}.log`。

### 迭代 2：跳躍障礙物與路徑重算
* **問題**：跟隨中遇到 1 格高障礙物時停滯無法跳過，被阻擋時不會繞路。
* **處理**：
  * 在 `src/actions/navigation.ts` 實作 `shouldJumpObstacle()`：依據機器人視角前方與水平碰撞狀態，檢測前方方塊頂部高度與頭頂空間，滿足條件時觸發 `bot.setControlState('jump', true)`。
  * 實作停滯偵測：若機器人與目標距離大於退出門檻但超過 1000ms 未產生位移，或尋路處於 Idle，自動觸發重新計算路徑。

### 迭代 3：1 格距離跟隨、高度判定、半磚/樓梯與攀爬支援
* **問題**：跟隨距離過遠，懸崖上下 XZ 距離近時誤退出，無法攀爬樓梯、半磚與梯子。
* **處理**：
  * 更新 `src/policy.ts`，設定 `followEnter: 2.2`、`followExit: 1.2`。
  * 退出條件改為 3D 距離與高度雙重校驗：`dist3D <= 1.2 && Math.abs(dy) <= 1.2`。
  * 實作 `getBlockTopY()`：利用方塊實際 bounding box shapes 計算精確頂部高度，半磚（0.5）與樓梯（0.5/1.0）高低差落在 (0.05, 1.25] 區間時均能正常觸發跳躍。
  * 實作 `isClimbingLadder()`：偵測當前或腳下為 ladder 或 vine，且主人高度大於機器人 0.3 格時，持續維持跳躍進行垂直攀爬。

### 迭代 4：開關門抖動與開門功能失效除錯
* **問題**：遇到關閉的門時頻繁開關（Flapping）；修復後又發生機器人完全不開門且跟隨停滯。
* **根因剖析**：
  1. **`pos.floored` 崩潰引發 200ms Cancel Loop**：
     * `navigation.ts` 內 `tryOpenDoorInFront` 等函式向 `bot.blockAt({ x, y, z })` 傳入了純 JS 物件。
     * Mineflayer / `prismarine-world` 內部執行 `pos.floored()`，因純物件無此方法而拋出 `TypeError: pos.floored is not a function`。
     * `executor.perform()` 捕獲錯誤，於次 Tick 呼叫 `stop(run)` 觸發 `adapter.cancel()`。
     * 行為樹隨即以新 runId 重新啟動動作，形成每 200ms 崩潰、取消、重啟的無窮迴圈，導致機器人無法移動亦無法開門。
  2. **單點探測與上半門激活問題**：
     * 舊版僅探測前方單一 0.8 格點，貼門或角度偏斜時遺漏。
     * 點擊上半門易導致伺服器判定不一致。
     * 原 `doorManager.reset()` 在 `adapter.cancel()` 時清空冷卻記錄，導致頻繁開關門。
* **解決方案**：
  1. 引入 `import { Vec3 } from 'vec3'` 並實作 `safeBlockAt(bot, pos)`，確保所有進入 `bot.blockAt` 的座標皆轉為具備 `.floored()` 的 `Vec3` 實例，杜絕崩潰。
  2. `DoorManager` 改採多距離射線（0.5, 0.9, 1.3, 1.7 格）於腳底與身體高度檢測，並在水平碰撞時探測相鄰方塊。
  3. 門已開啟狀態（`isDoorOpen`）絕對不重複互動。
  4. 偵測到門上半部（`half === 'upper'`）時，自動定位並激活下半門。
  5. 以門根部整數座標維護 1500ms 冷卻表，動作重啟不重置冷卻，防止抖動。
  6. 開門成功後立即更新 `lastRepathTime` 與目標，使尋路立即穿越門口。
  7. `src/perception.ts` 增加 `bot.entities` 備援檢索，確保主人實體不因短暫封包更迭中斷動作。
  8. `createExecutor` 接入 `logger`，確保動作執行期未預期異常完整記錄於日誌。

## 四、 Stage 4: 自動鄰近撿拾 (Opportunistic Pickup) 開發與驗收

### 1. 功能實作概述
* **掉落物感知探測**：
  * `src/perception.ts` 掃描 5 格（`THRESHOLDS.pickupRadius`）內掉落物實體（`item`, `Item`, `item_stack`）。
  * 支援提取掉落物名稱（透過 `getDroppedItem().name` 或 `displayName`）並按距離遞增排序寫入 `world.nearbyDrops`。
  * 支援接收 `cooldowns` 表，排除冷卻中的物品 ID。
* **行為樹優先級與狀態切換**：
  * 在 `src/bt/subtrees/work.ts` 中掛載 `PickupItem` (Priority 30)，位於 `CatchUpFollow` (40) 與 `NormalFollow` (20) 之間。
  * **非 Follow 狀態（STAY / IDLE）**：周圍 5 格有掉落物即主動靠近拾取，拾取完畢平滑回到待命。
  * **Follow 狀態**：主人在安全距離（<= 10 格）時順路插隊拾取，拾取完畢即刻無縫恢復跟隨主人；若主人跑遠（> 16 格），`CatchUpFollow` (40) 優先追趕主人，防止脫隊。
* **導航適配器與防死鎖防線**：
  * `src/actions/navigation.ts` 實作 `pickupItemAdapter`，以 `GoalNear(x, y, z, 0.8)` 導航。
  * 內建 4 秒逾時與 1.5 秒無位移停滯檢測，失敗時由 `executor.ts` 將實體 ID 寫入 30 秒 Cooldown 表，避免在圍欄等不可達目標前撞牆死鎖。
* **本體組裝與單元測試**：
  * `src/bot.ts` 註冊 `navigation.pickupItem`。
  * 新增 `test/unit/pickup.test.ts`，覆蓋感知過濾、模式切換、優先級搶佔與 Cooldown 觸發，全數 41 項單元測試通過。

### 2. 使用者實機測試回饋與後續優化分析
* **實機回饋**：平時與跟隨狀態下的自動撿拾功能可正常運作，但存在些許卡頓感，偶爾會有漏撿情況。
* **潛在成因剖析**：
  1. **拾取半徑與伺服器判定延遲**：
     * 當前 `GoalNear` 終點半徑為 0.8 格，尋路引擎到達 0.8 格即認定結束，但 Minecraft 伺服器對玩家拾取碰撞箱有微小延遲或需要靠得更近。
     * 若掉落物處於斜坡、水流推動或微小位移，靜態 `GoalNear` 未及時追蹤可能導致擦身而過未被吸入。
  2. **狀態切換之決策延遲**：
     * `PickupItem` 與 `NormalFollow` 之間的切換依賴 100ms 決策迴圈與 50ms 資源釋放緩衝（Fence），在主人持續快跑時，頻繁的搶佔與煞車會造成視覺上的頓挫。
* **後續優化指引**：
  * 靠近半徑微調至更貼身（例如 0.4~0.5 格）或目標到達判定時給予多 1~2 個 Tick 的停留吸取時間。
  * 若掉落物位置持續變動，在 `update()` 期間偵測位移並動態微調 Goal。
  * 考慮在極近距離（如 <= 1.2 格）且視野無障礙時，直接給予向前短衝而非完整重跑 Pathfinder 路徑規劃。

## 六、 Stage 6: 自動防禦反擊 (Self-Defense & Combat) 開發與驗收

### 1. 核心架構與設計考量
* **原生受控無外部依賴**：不引入 `mineflayer-pvp` 或第三方黑盒子，以純 TypeScript 依據鐵律實作 `Combat` 動作適配器。
* **四通道資源原子鎖定 (All-or-Nothing Allocation)**：
  * `Combat` (Priority 80) 要求 `{MOVE, LOOK, HAND, INVENTORY}` 四個通道。
  * 遭遇敵對威脅時，以 Priority 80 強制搶佔 `RoutineEat` (60) 與 `NormalFollow` (20) / `CatchUpFollow` (40)。
* **嚴格遵循 10 項鐵律**：
  * `[RULE-04]`：在 `bot.equip()` 與所有非同步操作後，嚴格檢查 `if (!ctx.isActive()) return;`。
  * `[RULE-06]`：嚴禁使用 `bot.pathfinder.goto` 或 `stop`，僅使用 `bot.pathfinder.setGoal(goal, true)` 與 `setGoal(null)`。
  * `[RULE-07]`：不在同一個 `runId` 的更新循環（`update`）中頻繁重複呼叫 `setGoal`，僅在啟動時設定 `GoalFollow(target, 2.5)`。
  * `[RULE-08]`：傷害來源安全推斷，透過 `HOSTILE_MOBS` 白名單與實體類型檢查，嚴禁主動反擊玩家（`type === 'player'` 或有 `username`）或被動/中立動物（牛、羊、豬、雞等）。

### 2. 交付元件與功能實作細節
* **敵對生物與受傷感知 (`src/perception.ts`)**：
  * 定義 `HOSTILE_MOBS` 白名單（殭屍、骷髏、蜘蛛、苦力怕、終界使者、掠奪者、守衛者等常見敵對生物）。
  * 實作 `isHostileMob()` 函式，嚴格排除玩家實體與非敵對生物（`[RULE-08]`）。
  * 在 `sample()` 中探測並過濾周圍已死亡（`health <= 0`）或無效（`isValid === false`）實體，將 16 格內威脅排序寫入 `world.threats`。
  * 透過追蹤 `bot.health` 變化設定 `world.self.tookDamageRecently`（受傷 2 秒內為 true）。
* **行為樹戰鬥子樹與遲滯 (`src/bt/subtrees/combat.ts`)**：
  * 進入門檻：周圍存在 8 格內（`THRESHOLDS.combatEnter`）之敵對生物。
  * 目標鎖定保持（Target Retention）：交戰中若現有目標距離拉大至 8~16 格（<= `THRESHOLDS.combatExit`），持續鎖定同一目標，防止目標稍微拉開或周圍刷怪時每 Tick 換目標產生狀態抽搐。
  * 脫戰門檻：
    * 目標死亡或脫離視線（`health <= 0` 或實體消失）。
    * 目標距離超過 16 格（`THRESHOLDS.combatExit`）。
    * 在跟隨狀態（`FOLLOW`）下，機器人與主人距離超過 24 格（`THRESHOLDS.combatMasterLimit`），防止機器人追怪過遠與主人走散。
* **戰鬥複合動作適配器 (`src/actions/combat.ts`)**：
  * 啟動期自動換裝：檢查手持武器，若背包有更高傷害之劍或斧，先執行 `await bot.equip(bestWeapon, 'hand')`，前後遵循 `[RULE-04]`。
  * 尋路與防破壞：設定 `movements.canDig = false` 防止追擊時揮手破壞方塊，並設定 `new GoalFollow(target, 2.5)` 進行動態追擊。
  * 瞄準與冷卻揮砍：在距離目標 `<= 3.5` 格時，以 550ms 節流（模擬 Minecraft 1.9+ 攻擊冷卻時間），透過 `bot.lookAt` 鎖定實體眼部高度並呼叫 `bot.attack(target)`。
  * 清理取消：`cancel()` 立即清除目標（`bot.pathfinder.setGoal(null)`）。
* **主控線程與受傷即時觸發 (`src/bot.ts`)**：
  * 註冊 `Combat` 適配器至 `executor`。
  * 監聽 Mineflayer `entityHurt` 事件，當受到傷害實體為機器人本體時，即刻呼叫 `sample()` 與 `runner.requestUrgentTick()` 觸發緊急決策。
* **單元與整合測試套件 (`test/unit/combat.test.ts`)**：
  * 敵對生物識別與玩家/中立生物排除驗證（`[RULE-08]`）。
  * 感知層威脅範圍與受傷標記驗證。
  * 行為樹戰鬥子樹進入、遲滯保持、超距脫戰、跟隨主人上限脫戰驗證。
  * 戰鬥動作適配器武器切換、追擊目標、550ms 攻擊冷卻節流與擊殺結束驗證。
  * 仲裁器搶佔驗證：`Combat (80)` 搶佔 `RoutineEat (60)` 與 `NormalFollow (20)`。

## 七、 Stage 7: 緊急逃跑功能 (Emergency Retreat) 開發與驗收

### 1. 使用者需求微調與核心設計
* **雙因子緊急撤退觸發**：
  * **因子一（殘血逃跑）**：機器人血量 `HP <= 6`（`THRESHOLDS.retreatHealth`）且 12 格內有敵對怪物。
  * **因子二（群怪包圍逃跑）**：不論當前血量高低，只要 12 格內敵對怪物數量達到 3 隻以上（`THRESHOLDS.retreatMobCount = 3`），判定為危急圍攻立即觸發撤退。
* **大範圍敵少安全點採樣演算法 (`findSafestEscapePosition`)**：
  * 以機器人當前位置為圓心、半徑 12 格採樣 16 個方位候選座標點。
  * 若提供地形感知，主動檢查候選點與腳下方塊是否為岩漿（Lava）或懸崖，排除危險地形。
  * 計算每個候選點周圍危險半徑（10 格）內的敵對怪物數量，以及至最近敵人的歐幾里得距離。
  * **選取準則**：優先挑選「周圍敵人數量最少（最理想為 0 隻）」的方位；若數量相同，挑選「離最近怪物距離最遠」的候選點。
* **整組搶佔中止 Combat**：
  * `Retreat` (Priority 100) 要求 `{MOVE, LOOK}`。
  * 當觸發逃跑時，仲裁器（Arbiter）以最高優先級整組中止 `Combat (80)`（釋放其持有的 `MOVE, LOOK, HAND, INVENTORY`），`Combat.cancel()` 即刻清空攻擊目標與尋路 Goal，嚴禁出現「身體在跑、手在回頭揮劍」的撕裂現象。
* **雙通道邊逃邊吃 (Action Blending)**：
  * `Retreat (100)` 僅佔用 `{MOVE, LOOK}`，`EmergencyEat (90)` 獲准同步取得 `{HAND, INVENTORY}`，實現一邊全速跑向安全點、一邊拿出食物進食補血。
* **退出遲滯 (Exit Hysteresis)**：
  * 進入撤退後，必須待「所有威脅距離 `>= 18` 格（`THRESHOLDS.retreatExit`）」或「`HP >= 10` 且周圍無群怪」才解除撤退，避免剛跑出 12.1 格又立刻回頭送死。

### 4. 實機測試異常分析與修復 (Retreat Freeze Bug Fix)
* **問題現象**：
  * 使用者回饋機器人在地下洞穴（Y = -60 深板岩層）遭遇史萊姆包圍時，成功觸發一次逃跑後即原地凍結不動（「逃跑一次後就當機了」），任由怪物攻擊長達數十秒直至伺服器切換和平模式。
* **Root Cause 根因分析**：
  1. **未驗證可行走地形 (Unwalkable Point / Wall Collision)**：
     * 地下洞穴空間受限，原 `findSafestEscapePosition` 僅在原高度 `origin.y` 採樣半徑 12 格之點，導致目標點落入深板岩/石頭岩壁內部。在 `canDig = false`（禁止破壞方塊）條件下，Pathfinder 判定 `'noPath'` 完全無法規劃路徑。
  2. **Mineflayer-Pathfinder 動態目標旗標問題 (Static Goal Bug)**：
     * 原 `bot.pathfinder.setGoal(activeGoal, true)` 對 `GoalNearXZ` 傳遞了 `dynamic = true`。當目標為靜態座標點時傳遞 `dynamic = true`，Pathfinder 會假設目標會持續移動而不會觸發 `goal_reached` 或路徑完成清理，導致狀態停滯（`isMoving === false`, `path.length === 0`）。
  3. **高優先級資源永久佔用與缺乏卡點自保機制 (Resource Deadlock / Trapped)**：
     * `Retreat`（Priority 100）高於 `Combat`（80）與 `Follow`（20）。在尋路停滯時，機器人永久鎖定 `{MOVE, LOOK}` 通道，導致既無法移動，也無法被 `Combat` 搶佔進行自衛還擊，演變為原地罰站捱打。
* **修復方案實作**：
  1. **可行走 Y 軸偵測與多段半徑退回 (`findWalkableY` & Multi-radius Fallback)**：
     * 實作垂直範圍 `[-4, +4]` 之足部/頭部非實體方塊（Air/Cave Air）與腳下實體立足點（非熔岩）驗證。
     * 若半徑 12 格全部被岩壁阻擋，依序自動降級至半徑 8 格與 5 格，確保在密閉洞穴中仍能取得有效空地座標。
  2. **靜態目標規範化**：
     * 將 `bot.pathfinder.setGoal(activeGoal)` 之 `dynamic` 參數修正為 `false`，確保靜態導航正確運作。
  3. **停滯偵測、重選安全方位與受困脫困保護 (Trapped Fail-safe)**：
     * 新增位移進度追蹤（`lastProgressTime`），若停留超過 1.2 秒或 Pathfinder 閒置超過 0.8 秒，自動避開原受阻方位（`avoidAngle`）重新採樣安全逃跑點。
     * **死角受困自保安全機制**：若連續停滯超過 3.5 秒（判定已被逼入死角無路可逃），`Retreat` 主動返回 `{ status: 'FAILURE' }` 中止逃跑，將通道歸還讓 `Combat (80)` 立即接管，使機器人能正面迎戰還擊，避免原地挨打致死。
  4. **主動開門支援**：
     * 整合 `DoorManager`，在逃跑路徑前方遇到木門或鐵門時主動開門，避免被封閉門戶阻擋。

## 八、 戰鬥子系統擴充: 玩家自衛反擊與 Owner 攻擊解除跟隨

### 1. 核心需求與行為規則
* **玩家納入戰鬥反擊範圍 (Self-Defense against Players)**：
  * 原先 `isHostileMob()` 遵循 `[RULE-08]` 排除所有玩家以防誤傷。現增設動態敵對目標機制（`DynamicHostileTarget`），僅在機器人實質受到玩家傷害時，將特定攻擊者暫時標記為威脅。
* **非 Owner 玩家攻擊懲戒 (Non-Owner 30s Hostile Chase)**：
  * 當受到非 Owner 玩家攻擊時，將該玩家標記為敵對威脅，維持 30 秒（`durationMs = 30000`）。
  * 機器人進入 `Combat` 模式進行追擊揮砍。若 30 秒內對方再次攻擊，計時重新刷新為 30 秒；若 30 秒到期且無後續受傷，或對方死亡/離線，自動脫戰。
* **Owner 攻擊處置 (Owner Unfollow & 1-Hit Counter-Attack)**：
  * 當受到 Owner 攻擊時：
    1. **立即解除跟隨**：意圖模式切換為 `STAY`（等同 `!unfollow`），終止跟隨行為。
    2. **回打一下**：Owner 被標記為短暫敵對目標，最長維持 3 秒，但限制僅回打 1 下（`maxHits = 1`）。
    3. **揮擊即脫戰**：機器人成功揮砍攻擊 1 次後，即刻將 Owner 從威脅清單移除，`Combat` 結束並保持在 `STAY` 待命狀態，不再緊黏主人。
* **攻擊者識別容錯 (Attacker Inference Fallback)**：
  * 監聽 `entityHurt` 中的 `source` 參數。若伺服器事件未提供 `source`（部分封包限制），透過 `entitySwingArm` 追蹤近身（<= 4.5 格）且剛揮手之玩家實體作為攻擊來源。

### 2. 交付元件與功能實作細節
* **感知層動態威脅管理 (`src/perception.ts`)**：
  * 新增 `DynamicHostileTarget` 介面與 `dynamicThreats` Map。
  * 提供 `recordAttacker(entity, config)` 支援設定持續時間與最大打擊次數。
  * 提供 `notifyAttack(targetId)` 於命中目標時消耗打擊次數，達標立即解除敵對。
  * `sample()` 自動過濾過期威脅，並將有效動態威脅與自然敵對生物一同匯入 `world.threats`。
* **戰鬥動作適配器擴充 (`src/actions/combat.ts`)**：
  * `createCombatAdapter` 新增 `options.isThreat` 與 `options.onAttack` 回呼支援。
  * 揮砍命中時觸發 `options.onAttack?.(targetId)`，且於目標不再是威脅時立即返回 `SUCCESS` 清理尋路。
* **主控線程整合 (`src/bot.ts`)**：
  * 監聽 `entitySwingArm` 記錄玩家揮手時間點。
  * 在 `entityHurt` 中識別攻擊者玩家，分別針對 Owner 執行 `runner.enqueue({ type: 'intent', mode: 'STAY' })` + 1 次反擊，與針對非 Owner 執行 30 秒追擊反擊。
* **單元與整合測試套件 (`test/unit/combat.test.ts`)**：

  * 新增非 Owner 玩家攻擊時追擊 30 秒並於過期脫戰測試。
  * 新增無 `source` 參數時藉由揮手事件推斷攻擊者測試。

## 九、 Stage 8: 指令系統重構與未知指令提示 (`!` 前綴與 Command Unknown)

### 1. 核心需求與行為規則
* **強制 `!` 指令前綴**：
  * 所有由 Owner 發送之指令必須以 `!` 作為前綴（例如 `!follow`、`!unfollow`、`!stop`、`!status`、`!state`）。
  * 一般未帶 `!` 之聊天訊息（如 `hello bot`、`follow me`）全數忽略，不作為指令解析，避免日常閒聊干擾機器人運行。
* **未知指令明確回覆**：
  * 當 Owner 發送以 `!` 開頭但未支援的指令（如 `!jump`、`!dance`）時，機器人於聊天室回覆 `command unknown`，提供清晰的使用者回饋。
* **權限維持**：
  * 僅 Owner 發送之 `!` 指令會被處理，非 Owner 發送者一律忽略。

### 2. 交付元件與功能實作細節
* **指令解析模組 (`src/commands.ts`)**：
  * 定義 `CommandEvent = { type: 'intent', mode } | { type: 'status' } | { type: 'unknown', raw: string }`。
  * `parseCommand()` 嚴格校驗 `message.trim().startsWith('!')`，截取前綴後轉換為標準指令或回傳 `{ type: 'unknown', raw }`。
* **主控線程整合 (`src/bot.ts`)**：
  * 當解析出 `event.type === 'unknown'` 時，透過 `chat.enqueue('command unknown')` 與 `requestUrgentTick()` 立即發送聊天回覆。
* **單元測試套件 (`test/unit/commands.test.ts`)**：
  * 驗證無 `!` 普通訊息忽略。
  * 驗證合法 `!` 指令與大小寫容錯。
  * 驗證未知 `!command` 解析出 `unknown` 並於聊天室回覆 `command unknown`。
